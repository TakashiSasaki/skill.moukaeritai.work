# Repository Template Bootstrap Instructions for Coding Agent

## 1. Task

Create an initial repository template for a schema, vocabulary, validation, catalog, and coding-agent-skill repository.

The repository must follow the design described in the accompanying specification document. The result should not be only empty directories. It must include one minimal but working example that demonstrates the intended lifecycle:

1. A small vocabulary definition.
2. A JSON Schema for a corresponding JSON document.
3. A JSON-LD context.
4. A SHACL shape.
5. A SQL DDL file.
6. A valid example and an invalid example.
7. A minimal coding-agent skill that explains how to work with the example schema.
8. A bundle definition for that skill.
9. A simple bundle builder script.
10. A validation script.
11. GitHub Actions workflows for validation and bundle publication.
12. Documentation explaining the structure and intended workflow.

The goal is to produce a repository that is immediately understandable, runnable, and extensible.

Do not create a large production ontology. Use a small toy domain that demonstrates the structure without introducing unnecessary domain complexity.

Recommended toy domain: `DocumentRecord`.

The example should model a simple record with these fields:

- `id`: stable identifier string.
- `title`: human-readable title.
- `createdAt`: ISO 8601 date-time string.
- `tags`: optional array of strings.

## 3. Required content

### 3.1 README.md

Create a root `README.md` that explains:

- This repository is the canonical source for schemas, vocabularies, validation tools, and coding-agent skills.
- `main` is the only editable canonical branch.
- Distribution branches use the `dist/` prefix.
- Distribution branches are generated by CI.
- Distribution branches are intended to be orphan branches.
- Downstream users should import `dist/skills/<name>` branches as Git submodules.
- The included `DocumentRecord` example is intentionally small and demonstrates the pattern.

Include this example command:

```bash
git submodule add -b dist/skills/document-record-authoring \
  https://github.com/TakashiSasaki/skill.moukaeritai.work.git \
  .agents/skills/document-record-authoring
```

Use placeholder repository URLs such as `https://github.com/TakashiSasaki/skill.moukaeritai.work.git`.

### 3.2 LICENSE

Create an MIT license file using a placeholder copyright holder:

```text
Copyright (c) YEAR OWNER
```

### 3.3 JSON Schema

Create `specs/json-schema/document-record.schema.json`.

Requirements:

- Use JSON Schema draft 2020-12.
- Include an absolute placeholder `$id`.
- Define object type.
- Required fields: `id`, `title`, `createdAt`.
- Optional field: `tags`.
- `id`: string, non-empty.
- `title`: string, non-empty.
- `createdAt`: string, `format: date-time`.
- `tags`: array of non-empty strings.
- Disallow additional properties.

Use an `$id` like:

```text
https://example.org/schema/json/document-record.schema.json
```

### 3.4 RDF/Turtle vocabulary

Create `specs/vocab/core.ttl`.

Requirements:

- Define a small vocabulary namespace, for example `https://example.org/vocab/core#`.
- Define `DocumentRecord` as an RDFS class.
- Define properties `id`, `title`, `createdAt`, and `tag`.
- Use `rdfs:label`, `rdfs:comment`, `rdfs:domain`, and `rdfs:range` where appropriate.
- Keep the vocabulary intentionally simple.

### 3.5 JSON-LD context

Create `specs/mappings/jsonld/document-record.context.jsonld`.

Requirements:

- Map `DocumentRecord`, `id`, `title`, `createdAt`, and `tag` to the vocabulary terms.
- Include an `@vocab` or explicit term mappings.
- Map `createdAt` to `xsd:dateTime`.

### 3.6 SHACL shapes

Create `specs/shacl/document-record.shacl.ttl`.

Requirements:

- Define a node shape for `DocumentRecord`.
- Require exactly one `id`.
- Require exactly one `title`.
- Require exactly one `createdAt`.
- Allow zero or more `tag` values.
- Use `xsd:string` and `xsd:dateTime` datatypes appropriately.

### 3.7 SQL DDL

Create `specs/sql/document-record.sqlite.sql`.

Requirements:

- Target SQLite.
- Define a `document_record` table.
- Include `id TEXT PRIMARY KEY`.
- Include `title TEXT NOT NULL CHECK (length(title) > 0)`.
- Include `created_at TEXT NOT NULL`.
- Include a separate `document_record_tag` table for tags.
- Include a foreign key from `document_record_tag.document_id` to `document_record.id`.

### 3.8 Catalog

Create `catalog/catalog.jsonld`.

Requirements:

- Use JSON-LD.
- Include entries for the JSON Schema, vocabulary, JSON-LD context, SHACL shape, SQL DDL, skill, and bundle definition.
- Keep it small and readable.
- It does not need to be a complete DCAT implementation yet, but use terms such as `@id`, `@type`, `name`, `path`, `kind`, and `version` consistently.

### 3.9 Examples

Create a valid example:

```text
examples/valid/document-record.json
```

It should include all required fields and at least one tag.

Create an invalid example:

```text
examples/invalid/document-record-missing-title.json
```

It should be invalid because `title` is missing.

### 3.10 Skill

Create:

```text
skills/document-record-authoring/SKILL.md
```

Requirements:

- Include YAML front matter with `name` and `description`.
- Name must be `document-record-authoring`.
- Description should explain when the skill should be used.
- Explain that schemas are canonical and the skill is operational guidance.
- Instruct the agent to read `references/schema-sources.md` before editing.
- Instruct the agent to run `python tools/validate_all.py` in the canonical repository.
- In a distribution bundle, instruct the agent to use bundled `references/specs/` and `scripts/` paths if present.
- Explicitly state that generated distribution branch files should not be edited directly.

Create:

```text
skills/document-record-authoring/references/schema-sources.md
skills/document-record-authoring/references/validation-rules.md
```

These files should explain where the canonical sources are and how to validate them.

### 3.11 Bundle definition

Create:

```text
bundles/skills/document-record-authoring.yaml
```

The bundle definition must describe a self-contained skill bundle to be published to:

```text
dist/skills/document-record-authoring
```

It must include:

- `skills/document-record-authoring/` to bundle root.
- JSON Schema snapshot under `references/specs/json-schema/`.
- vocabulary snapshot under `references/specs/vocab/`.
- SHACL snapshot under `references/specs/shacl/`.
- JSON-LD context snapshot under `references/specs/mappings/jsonld/`.
- catalog snapshot under `references/catalog.snapshot.jsonld`.
- validation script under `scripts/validate_all.py` or `scripts/check_document_record.py`.
- generated `references/bundle-lock.json`.

Use this approximate shape:

```yaml
schemaVersion: 1

bundle:
  name: document-record-authoring
  kind: skill
  source: skills/document-record-authoring
  outputBranch: dist/skills/document-record-authoring

include:
  - from: skills/document-record-authoring/
    to: ./
    mode: copy
  - from: specs/json-schema/document-record.schema.json
    to: references/specs/json-schema/document-record.schema.json
    mode: copy
  - from: specs/vocab/core.ttl
    to: references/specs/vocab/core.ttl
    mode: copy
  - from: specs/shacl/document-record.shacl.ttl
    to: references/specs/shacl/document-record.shacl.ttl
    mode: copy
  - from: specs/mappings/jsonld/document-record.context.jsonld
    to: references/specs/mappings/jsonld/document-record.context.jsonld
    mode: copy
  - from: catalog/catalog.jsonld
    to: references/catalog.snapshot.jsonld
    mode: copy
  - from: tools/validate_all.py
    to: scripts/validate_all.py
    mode: copy

generate:
  lockFile: references/bundle-lock.json
  readme: README.md

validation:
  requireFiles:
    - SKILL.md
    - references/bundle-lock.json
    - references/specs/json-schema/document-record.schema.json
  checkNoSymlinks: true
```

### 3.12 Validation tool

Create `tools/validate_all.py`.

Requirements:

- Python 3.11+ compatible.
- Use only standard library if practical.
- Validate that required files exist.
- Validate valid JSON example using a minimal built-in check if no external dependency is used.
- Validate that invalid JSON example fails because `title` is missing.
- Parse JSON files.
- Check that the catalog exists and contains references to important files.
- Check that no generated bundle files are being treated as canonical in `main`.
- Print clear pass/fail messages.
- Return non-zero exit code on failure.

Do not implement full JSON Schema validation unless adding a dependency management file such as `pyproject.toml`. For the initial template, a structural validator is acceptable.

### 3.13 Bundle builder

Create `tools/bundle/build_bundles.py`.

Requirements:

- Python 3.11+ compatible.
- Read bundle YAML files.
- If PyYAML is not available, either use a very small limited parser for the included example or document that PyYAML is required.
- Generate bundle contents into an output directory, for example `.bundle-out/`.
- Copy included files according to `include` rules.
- Reject absolute paths.
- Reject `..` path traversal.
- Generate `references/bundle-lock.json`.
- Do not include timestamps in the lock file.
- Include source commit if available from `git rev-parse HEAD`; otherwise use `unknown`.
- Preserve deterministic output as much as possible.

### 3.14 Bundle definition validator

Create `tools/bundle/validate_bundle_definitions.py`.

Requirements:

- Validate that each bundle definition has `schemaVersion`, `bundle.name`, `bundle.kind`, `bundle.source`, `bundle.outputBranch`, and `include`.
- Validate that `bundle.outputBranch` starts with `dist/`.
- Validate that every `include[].from` exists.
- Validate that no `include[].to` escapes bundle root.

### 3.15 Publish script placeholder

Create `tools/bundle/publish_bundle_branches.py`.

Requirements:

- It may be a safe placeholder in the initial template.
- It must document the intended algorithm:
  1. Fetch target `dist/*` branch.
  2. If absent, create orphan branch.
  3. If present, checkout existing branch.
  4. Replace tree with generated bundle.
  5. Commit only if there is a diff.
  6. Push to `dist/*`.
- It must not push anything unless explicitly invoked with a flag such as `--push`.

### 3.16 GitHub Actions

Create `.github/workflows/validate.yml`.

Requirements:

- Run on pull request and push to `main`.
- Checkout repository.
- Set up Python.
- Run `python tools/validate_all.py`.
- Run `python tools/bundle/validate_bundle_definitions.py bundles/`.
- Run `python tools/bundle/build_bundles.py --all --out .bundle-out`.

Create `.github/workflows/publish-bundles.yml`.

Requirements:

- Run on push to `main` and manual dispatch.
- Checkout with full history.
- Set up Python.
- Run validation.
- Build bundles.
- Include a commented or disabled publish step if necessary.
- Explain in comments that real publishing to `dist/*` orphan branches should be enabled after repository permissions and branch protections are configured.

## 4. Constraints

### 4.1 Do not overbuild

This is a template. Keep the example small.

Do not introduce a large ontology framework, package manager, or complex release automation unless necessary.

### 4.2 Prefer deterministic files

Avoid generated timestamps and environment-specific absolute paths.

### 4.3 Do not require recursive submodules

The generated skill bundle should be self-contained. It must not require nested submodules.

### 4.4 Do not make `dist/` branches editable sources

All generated distribution branch content must clearly state that it is generated and should not be directly edited.

### 4.5 Do not place canonical schema files inside skill `assets/`

Canonical schema files belong under `specs/`. Bundled schema snapshots belong under `references/specs/` in a distribution bundle.

### 4.6 Use placeholder URIs consistently

Use `https://example.org/` and `https://github.com/TakashiSasaki/skill.moukaeritai.work.git` as placeholders. Do not invent real ownership.

## 5. Acceptance criteria

The task is complete when all of the following are true:

1. The required directory structure exists.
2. The repository has one coherent `DocumentRecord` example spanning JSON Schema, RDF vocabulary, JSON-LD context, SHACL, SQL, examples, catalog, skill, and bundle definition.
3. `python tools/validate_all.py` succeeds.
4. `python tools/bundle/validate_bundle_definitions.py bundles/` succeeds.
5. `python tools/bundle/build_bundles.py --all --out .bundle-out` creates a self-contained bundle directory.
6. The generated bundle includes `SKILL.md`, `references/bundle-lock.json`, schema snapshots, catalog snapshot, and validation script.
7. The generated bundle does not contain symlinks.
8. The generated bundle does not depend on recursive submodules.
9. Documentation clearly distinguishes canonical sources on `main` from generated distribution branches under `dist/*`.
10. The repository can serve as a practical starting point for expanding to real schemas and skills.

## 6. Implementation notes

Use simple Python scripts and plain files. Prefer clarity over cleverness.

If a dependency such as PyYAML or jsonschema is introduced, create a minimal `pyproject.toml` and document how to run the tools. If no dependency file is created, scripts should rely only on the Python standard library.

For the first template version, it is acceptable for validation to be structural rather than a complete standards-compliant JSON Schema / SHACL validation implementation. The template should make it easy to replace the simple validators with real validators later.

## 7. Expected final response from the coding agent

After creating the repository template, summarize:

1. Files created.
2. How to run validation.
3. How to build bundles.
4. How downstream developers would add the generated skill branch as a submodule.
5. Which parts are placeholders that should be customized before publication.

Do not claim that real `dist/*` branches have been published unless the publish script was actually run with push permission and succeeded.
